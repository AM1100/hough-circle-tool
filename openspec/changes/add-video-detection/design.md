# Design
## Context
当前基线 dc37779：app.py 支持图片 CLI 和 /api/detect；detector.detect 接收编码图片 bytes，内部完成解码、检测及PNG编码；web/index.html 仅接受图片。已有视频文件路径不能作为图片输入使用。本次任务是交出准备，不实施上述新需求。
## Goals / Non-Goals
**Goals:** 复用现有霍夫参数与检测逻辑，给接手人一个离线视频闭环和可验证的帧级合同。
**Non-Goals:** 本次不写视频程序；后续首版不做实时相机、丢帧策略、音频保留、跟踪器或新圆检测算法，不声称既有图片预设能直接适配新视频。
## Decisions
- 首版离线逐帧处理，比实时队列方案更容易核对完整性，符合“导入视频完成检测”的交接目标。
- 后续先提取接收 ndarray 的单帧核心，现有 bytes API 保持包装兼容；不对每帧做无必要的JPEG/PNG往返。先跑图片回归，再接视频读写。
- 拟新增 video.py 管理 VideoCapture/Writer 生命周期、帧序号和逐帧 JSONL；app.py 负责参数校验、任务响应和结果下载；web/index.html 负责文件选择与状态。把读写/检测/展示分开，避免把视频循环塞进当前HTTP处理器。
- MP4 无音轨作为明确首版边界；帧率无效时拒绝而不猜测，避免伪造视频时间。无圆逐帧留空，不用历史坐标代替当前检测。
- JSONL 每帧一行，circles 是列表，能表达零个、一个或多个圆；比每个圆一行的CSV更易保留无圆帧。
## Risks / Trade-offs
- 编解码器和FPS差异 → 接手时先用指定短视频做只读/只写MVP，记录真实总帧数和FPS。
- 现有预设只针对两张固定尺寸照片 → 新视频参数效果尚未验证，必须选代表性帧人工核对；不得写死圆数。
- 视频体积与处理时间超出现有24MiB请求限制 → 在接手实施阶段按短视频MVP的实测决定上传上限与任务生命周期，不能直接放开全局限制。
- 当前浏览器导出路径只适用于data URL图片 → 视频需结果文件下载与清理机制；并发、取消、长视频资源使用暂未测试，不做可用性承诺。
## Migration Plan
在本分支接续 add-video-detection 变更；先通过既有5项测试，再完成 tasks.md 未勾选项。每步保存真实命令、输出与失败证据；完成后才更新视频能力状态。原图片基线记录继续保留。
